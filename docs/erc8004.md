# Base check + ERC-8004 reputation writer

Two parts for the "insert a check between search and pay" theme:

- **A. vet402 check** (`skills/vet402-check/`, `src/check/vet402-check.ts`, `scripts/vet402-check.ts`): the step between `awal x402 bazaar search` and `awal x402 pay`. Read-only.
- **B. ERC-8004 reputation writer** (`src/evm/erc8004.ts`, `scripts/erc8004-simulate.ts`): writes "vet402 paid it and it was delivered", with the tx, as ERC-8004 feedback. **Encode, eth_call and eth_estimateGas only. There is no signing or sending code**, and a test fails if any appears.

All facts below were read on 2026-09-28 (JST).

## B. ERC-8004

### What the spec actually says (the assumption that was wrong)

`proofOfPayment` is **not** an argument of `giveFeedback`. From the EIP text (ethereum/ERCs `ERCS/erc-8004.md`, status Draft):

```solidity
function giveFeedback(uint256 agentId, int128 value, uint8 valueDecimals, string tag1, string tag2,
                      string endpoint, string feedbackURI, bytes32 feedbackHash) external
```

`proofOfPayment {fromAddress, toAddress, chainId, txHash}` is a field of the OPTIONAL off-chain feedback file that `feedbackURI` points to. `feedbackHash` = keccak256 of that file. The writer therefore:

1. reads the purchase tx receipt on Base and takes `fromAddress` from the USDC `Transfer` log (it is not typed in), checking the recipient and the amount;
2. builds the feedback file (MUST fields + `proofOfPayment` + a `vet402` block: attemptedAt, amount, HTTP status, L2, evidence URL);
3. by default puts the file in a `data:application/json;base64,` feedbackURI, so the proof is inside the `NewFeedback` log and needs no host; an external URI can be passed instead;
4. `value` = 1 (delivered) or 0, `valueDecimals` 0, `tag1` `x402Delivered`, `tag2` `vet402-L1`, `endpoint` = the seller URL.

Before a real write, `preflight` must show all of: `getIdentityRegistry()` is the expected registry, `isAuthorizedOrOwner(submitter, agentId)` is false (the spec forbids owner/operator self-feedback, and the contract reverts on it), and `sellerBinding` is `agentWallet` or `owner`, meaning the agent's wallet is the payTo vet402 paid. Without a binding the plan says "do not write".

## Solana 8004 (QuantuLabs/8004-solana): can it be written the same way?

Yes, in the same shape, with these differences (source: repo README, `idl/agent_registry_8004.json`, `programs/agent-registry-8004/src/{lib.rs,reputation/instructions.rs,reputation/state.rs,reputation/seal.rs}`, main @ 2026-09-10):

| | EVM (ERC-8004) | Solana (8004-solana) |
| --- | --- | --- |
| Program / contract | ReputationRegistry proxy per chain | one program `agent-registry-8004`: mainnet `8oo4dC4JvBLwy5tGgiH3WwK4B9PWxL9Z4XjA2jzkQMbQ` (README + `declare_id!`), devnet `8oo4J9tBB3Hna1jRQ3rWvJjojqM5DYTDJo5cejUuJy3C`; ATOM engine mainnet `AToMw53aiPQ8j7iHVb4fGt6nzUNxUhcPc3tbPBZuzVVb` |
| Agent id | `uint256` token id | Metaplex Core asset pubkey |
| Args | value, valueDecimals, tag1, tag2, endpoint, feedbackURI, feedbackHash | value `i128`, value_decimals `u8`, **score `Option<u8>` (0 to 100, feeds ATOM)**, feedback_file_hash `Option<[u8;32]>`, tag1, tag2, endpoint, feedback_uri |
| Length limits | none in the contract | tag ≤ 32 bytes, endpoint ≤ 250, **feedback_uri ≤ 250 bytes** |
| File hash | keccak256 | keccak256 (`seal.rs`), so the same file bytes and hash can be reused |
| Self-feedback rule | owner or approved operator reverts | only the Core owner is refused (`SelfFeedbackNotAllowed`) |
| Storage | value/decimals/tags stored, URI and hash in the event | events only, with a SEAL v1 hash chain; reads need their indexer |
| Index | per client, 1-based | global per agent, 0-based |
| Cost | ~244k gas | ~0.000005 SOL per the README (tx fee; no rent listed) |

What changes for vet402: the inline `data:` URI (~1.1 KB) does not fit in 250 bytes, so on Solana the feedback file must be hosted (IPFS or an https path) and passed by hash. The rest (proofOfPayment in the file, keccak256 commitment, value 1/0, tags) carries over unchanged. The Solana writer (`scripts/solana-feedback.ts`) sends no score and no ATOM accounts; that form was checked by simulateTransaction on mainnet on 2026-09-29 (fee only).

## Base buy + feedback (dry-run built and run; --pay / --write not run)

- `scripts/base-buy.ts`: buys once per seller from `0x9B59…4E51` (x402 v2 `exact`, EIP-3009 only). Candidates: ERC-8004 agents on Base whose on-chain `getAgentWallet` is the payTo of a Bazaar listing vet402 already bought and got a 2xx from (`vet402.com/api/v1/observatory/export.csv?days=30`). Guards before any signature: 0.10 per purchase, 1.00 total, 10 purchases, one per payTo (`results/base-ledger.json`, fail-closed), payTo locked to the unpaid 402 and to agentWallet (re-read at pay time), price may only drop, Base USDC with domain `USD Coin`/`2` (read from the token), `assetTransferMethod` must be EIP-3009, `maxTimeoutSeconds` ≤ 3600. The key can only sign that one `TransferWithAuthorization` (`fencedSigner`) and has no transaction path. The signature is verified against the payer before it leaves. Settlement is re-read on Base (USDC Transfer payer → payTo, amount).
- `scripts/base-feedback.ts`: `giveFeedback` on Base from the same address that paid, so the payer and the submitter are the same on chain. `feedbackURI` = data: URI, `proofOfPayment.txHash` = that purchase's settlement tx. `--write` takes only records that were sent, answered 2xx with a body, and settled on chain. It also requires agentWallet = payTo, a submitter that is not the owner or an operator, no earlier feedback from this address, no earlier write of the same tx, a passing simulate, and ETH ≥ 1.5× the max-fee cost.
- Both need an extra env switch (`VET402_BASE_PAY=yes`, `VET402_BASE_WRITE=yes`) on top of the flag. Dry runs use a throwaway signing key and never open the key file.
- Results: `results/base-buy-dryrun.json` (8 would_pay, 0.044 USDC in total), `results/base-feedback-dryrun.json` (8 simulate ok, gas 227,808 to 245,201, placeholder tx).
